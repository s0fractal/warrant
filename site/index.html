Warrant 3 · 3.0.0a2 · alpha

Signed records of work, judged by the reader.

Warrant keeps work as signed records: what a thing is (one version of a claim, an obligation, a pull request head), who accepted it, who objected and with what counterexample. Each reader judges the same bytes under its own trust — which keys are whose — and profile — who holds which role — and gets one answer: what may be relied on now, what still waits, and for whom.

pip install --pre warrant-graph

Python ≥ 3.10; depends only on cryptography. Adds the commands warrant, warrant-agent and, with [mcp], warrant-agent-mcp. Alpha: record formats and interfaces may still change.

The model

One record envelope with four kinds, native lineage, schemas that are records themselves, one guard, and one pure function, assess.

KindSays
schemathe rules of one schema: its fields, its states, the minimal guard each state needs, who may enter which state
entityone version of a thing in a lineage; body.state is its state
attestan actor's statement about one record: an acceptance, a replay result
challengea counterexample or objection against one record

A lineage's state is that of its newest version whose guard is met. Two versions succeeding one version fork the lineage. A challenge from an actor with a role in the guard lowers reliance until a later version is accepted. Reliance is ELIGIBLE, PENDING, CHALLENGED or FORK. A key authenticates; it authorizes nothing: roles are the reader's profile.

Where it runs today

  • On itself. The normative sentences of the spec are claim records, each with the tests that witness it and the mutants those tests kill. A claim counts once the claims checker has run them at a commit and signed its acceptance. Pull request reviews are records too, and a gate merges a pull request on a recorded acceptance. How the repository works.
  • On another repository. interdict-mesh, a Rust/eBPF network node, keeps its invariant contracts as lineages in its own store, pinned by the owner's signed manifest, and its pull request reviews as Warrant records, using the review loop that ships in the package.

Limits

  • A store cannot prove its own completeness; every report says so (UNATTESTED).
  • An assessment has admission limits; beyond one it is refused, never answered in part.
  • Not in this version: grants, schedules, triggers, merge rules for a forked lineage, threshold adoption, key rotation.
  • One implementation (Python). Reviews so far are by model reviewers; no external security audit is recorded.

The spec's §11 says what was dropped from Warrant 2 and why; §12 what is open.
