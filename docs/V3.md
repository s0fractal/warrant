# Warrant 3 — specification

**Status:** the normative specification of this repository's format since the switch from
Warrant 2 (2026-10-27; docs/HISTORY.md): `warrant/` implements it, `.warrant/records.jsonl` is its store,
and its normative sentences are `claim@1` records (`python3 tools/claims.py view`; §15). Warrant 2
(SPEC.md 2.0.0a1, `warrant-graph` 2.0.0a1 on PyPI) is history, at the tag
`history/warrant-2-2026-10-27`. Key words MUST / MUST NOT / MAY per RFC 2119.

Warrant 3 is one small core over one record envelope. The domain rules that Warrant 2's
repository tools re-implement three times (claims, roadmap, reviews: lineage, forks, acceptor
terms, acceptance indexes) become one lineage rule in the core and data in the store: schema
records. What a receiver relies on is still its own verdict, under its own trust and profile.

## 1. Encoding

As Warrant 2 §2: JSON values without floats, integers within ±(2^53−1), no lone surrogates;
canonical bytes are RFC 8785 (JCS); hashes are lowercase hex SHA-256; time is integer Unix seconds.
The implementation's `warrant/jcs.py` and `warrant/keys.py` are Warrant 2's, unchanged.

## 2. The record

```json
{"warrant": "3", "kind": K, "actor": A, "at": T, "prev": ID|null, "schema": NAME|null,
 "lineage": ID|null, "refs": [HEX64…], "guard": GUARD|null, "body": {…}}
```

All ten members are required; no other member is allowed. The record's **id** is
`sha256(canon(record))`. A record is stored as the canonical line
`canon({"record": R, "sig": S})`, where `S` is `{"key": <key id>, "ed25519": <hex128>}` over the
bytes `"warrant-sig-v3:" || id_raw`, or `null` for a migrated record (§9). The v3 domain prefix
differs from v2's `warrant-sig-v1:`: no v2 signature verifies as a v3 one.

- `actor`: an actor id as in Warrant 2 §3 (NFC, ≤ 200 code points, no control character, no
  surrounding white space).
- `prev`: the id of this actor's previous signed record, or null for its first (§7).
- `refs`: a sorted list of distinct hex64: the records and blobs this record depends on. A body
  field of a reference type (§4) MUST also appear in `refs`. The graph's edges are read from
  `refs`, `lineage`, `guard.requires` and `prev`, never from free text.
- `body`: an object; its canonical bytes are at most **16 384** bytes. Larger content is a
  blob (§8) named in `refs`.
- `guard`: §6.

**Kinds** (four):

| kind | says | `schema` | `lineage` | `body.target` |
| --- | --- | --- | --- | --- |
| `schema` | the rules of one record schema (§4) | null | an earlier version of the same schema | — |
| `entity` | one version of a thing: a claim, a goal, an obligation, a pull request | required | the version it replaces, or null | — |
| `attest` | an actor's statement about one record: acceptance, a replay result, an observation | optional | null | the record attested |
| `challenge` | a counterexample or objection against one record | optional | null | the record challenged |

An `attest` or `challenge` MUST name its target in `body.target` (also in `refs`; `refs` is sorted,
so no position in it can name the target) and have a null `lineage` and `guard`.

## 3. Lineage

A record whose `lineage` is L **succeeds** L. L MUST be in the view, of the same kind and the same
schema; otherwise the record is **excluded** from every lineage (`LINEAGE_BROKEN`). The records
reachable through `lineage` from a record with `lineage: null` (its **root**) form the root's
lineage; the lineage is named by its root's id. Because an id covers `lineage`, a version is
always newer than what it names: lineages are acyclic by construction, and no clock orders them.

- **Who may succeed.** A successor entering a state the schema's `successors` names MUST be
  filed by an actor holding one of the roles named for that state under the receiver's profile
  (§10), and only by such an actor; a successor entering any other state MUST be filed by the
  root's actor. Otherwise it is excluded (`LINEAGE_NOT_AUTHOR`). `obligation@1` names
  `released`: the owner, to whom the obligation is owed, releases it alone and the holder
  cannot (Warrant 2 §4.1's release, by the creditor only). This one rule replaces `LINEAGE_NOT_AUTHOR` (claims),
  `REVIEW_HEAD_FILER` (reviews) and the author check of roadmap revisions.
- **FORK** is a core verdict. Two admitted records succeeding the same record fork the lineage:
  the lineage's verdict is `FORK`, every branch is listed, and no record is excluded for it (as
  Warrant 2 §4 keeps both branches of a chain fork: exclusion would let a forker retract its own
  earlier records). A forked lineage has no leaf and no state. This replaces `FORK`,
  `GOAL_FORK`, `REVIEW_HEAD_FORK` and `FINDING_FORK`.
- **Leaf**: the one version with no admitted successor. **Effective version**: the newest version
  on the path from the root to the leaf whose guard is met or absent (§6). The lineage's
  **state** is the effective version's `body.state` (null when none is effective). The leaf
  being pending while an earlier version is effective is how a proposal waits: a closure that
  was admitted stays history (Warrant 2 §4.3), and a reformulation that is not yet accepted
  changes nothing.
- A successor dated before what it succeeds is listed (`LINEAGE_BACKDATED`) and still counts:
  the id, not `at`, witnesses the order.

## 4. Schemas are records

A `schema` record's body:

```json
{"name": "claim@1",
 "fields": {"state": "str", "text": "str", "witnesses": "strs", "reason": "str?", "answers": "ref"},
 "states": {"unbacked": null, "backed": GUARD},
 "closed": ["backed"],
 "successors": {}}
```

- `fields`: the closed set of body members and their types: `str`, `int`, `bool`, `strs` (list
  of strings), `ref` (hex64), `refs` (list of hex64), `obj` (any JSON value); a trailing `?` makes
  the member optional and nullable. Members of type `ref`/`refs` MUST appear in the record's `refs`.
- `states` (entities only): the allowed values of `body.state`, each with the **minimal guard**
  a version entering that state MUST carry (null: none).
- `closed`: the states that close the lineage for `guard.requires` (§6).
- `successors`: `{state: [roles]}`, the states only those roles may enter (§3).

A body that does not fit its schema makes the record `INVALID` (listed, counted nowhere). A
schema record counts only when at least k distinct actors holding the role `schema/author` in
the receiver's profile stand behind it: its filer, and every such actor that attests it with
`"verdict": "accept"`. k is the profile's `quorum["schema/author"]` (1 when absent). With k ≥ 2
no single actor can add or change a schema. A schema short of its quorum is listed under
`schemas_pending` with who backs it. The leaf of a schema lineage (successors by its root's actor) is used, and a forked
schema lineage is `SCHEMA_CONFLICT`. Two counted schema lineages naming the same `name` are
`SCHEMA_CONFLICT` too, and every record of that name is invalid until one is retired. Schemas are resolved over the whole view, not by position. The name `migration@1` is
reserved by the core (§9).

Only an attest without a schema stands behind a schema record, so an attest the body check drops (`INVALID`) never makes up a quorum.
A well-formed schema short of its quorum is a proposal, not a problem of the store: only a schema whose body is not a schema body is `SCHEMA_NOT_COUNTED`.
A record of `migration@1` that is not an attest is `INVALID`.

`warrant bootstrap` files the schemas `claim@1`, `goal@1`, `obligation@1`, `pr-head@1` and
`finding@1` (`warrant/bootstrap.py`). A new domain is a new schema record; it needs no code.

## 5. Attest and challenge

An `attest` by actor A **on** record X (its `body.target`) states A's position on exactly X's bytes:
because X's id covers its evidence, accepting a version accepts exactly its evidence set
(Warrant 2 §3.3's binding, by construction). An acceptance's body carries `"verdict": "accept"`; a
replay result's carries `{"verdict": "reproduces" | "does_not_reproduce" | "no_result" |
"does_not_apply", "on": <version id>}`. An attest names the record it attests, so it is always
newer than it; an attest by X's own actor never counts toward X's guard.

A `challenge` against X **counts** when its actor is X's actor, holds a role in X's guard, or
holds the profile role `challenger`; or when it is **reproduced**: an actor holding the role
`replayer` attests `reproduces` on the challenge with `on` equal to X. Whoever filed a
reproduced challenge does not matter (Warrant 2 §4.4's evidence-weighted challenge, without the
observe condition). A counted challenge **stands** until a version after X in its lineage is
effective (an X in no lineage: always); a successor answers it once it is accepted, as Warrant 2's
revalidation does. Challenges never rewrite a guard verdict: they lower
reliance (§10), as in Warrant 2 §4.3.

## 6. Guard

```json
{"quorum": N, "roles": [ROLE…], "match": {FIELD: VALUE…}, "requires": [LINEAGE…]}
```

All four members are required. A version's guard is **met** iff

1. at least `quorum` distinct actors, none of them the version's actor, each holding a role in
   `roles` under the receiver's profile, filed an authentic `attest` on the version whose body
   has every `match` member with an equal value; and
2. if the version's state is in its schema's `closed`, every lineage in the accumulated
   `requires` (this version's and every earlier version's in its lineage: requires only grow)
   has an effective state in its own schema's `closed`.

Otherwise it is `PENDING`, with what it waits for. Rule 2 holds for every version entering a
closed state, with or without a guard: a guardless closure whose requirements are open is
`PENDING`, never effective. Any other version without a guard is effective as filed. A version whose guard is weaker than its schema's minimal guard for its state
(smaller quorum, a role outside the schema's, a `match` member missing or different, a missing
`requires`) is `INVALID`.

Rule 2 is resolved for all versions at once, as a least fixpoint: a closing version is met only once every lineage it requires has a closing effective version that is met first, so the verdicts do not depend on the order of record ids, and each version's guard agrees with its lineage's effective version.
A cycle in `requires` that no version outside it closes resolves to PENDING; no version in a cycle satisfies another.

One guard replaces `attest`, `observe`, `compute` and the claims tool's `by_replay`. Who
attests decides what the attestation is worth: a person with a role, or a **checker** — a program
holding a role under a stable actor id, its key bound once. A checker's attest body names what
produced it: `code`, the digest of everything that decides its output, and `env`, the versions of
the interpreter and libraries that digest leaves out. `code` MUST cover the checker's whole import
closure (every module it loads from its repository, refused when one lies outside the hashed tree),
not one file: a partial identity lets bytes the digest does not name decide the result.
"Replayed" stays a verifiable property: anyone may re-run the code `code` names at the commit the
attest names and compare. A change to the checker's code changes the `code` its attests name, never
its actor. The migrator (§9) predates this rule: its actor is named by its code's digest.

## 7. Actor chains

Each actor's signed records form its chain through `prev` (Warrant 2 F43). A record is chained
iff its `prev` is null and it is that actor's only genesis, or `prev` names a signed record of the
same actor in the view not dated after it. Two records naming the same `prev`, or two genesis
records of one actor, are a chain fork: listed, nothing excluded. A writer's head is the chained
record no other of its records names, found through the `prev` links themselves: records filed in
one second follow their chain, never their time. A writer takes `prev` from its head under the
writers' exclusive lock on the store directory, and refuses to date a record before it;
`--expect-head` makes the append a compare-and-swap. Migrated
records (`sig: null`) are in no chain. No rule of §§3–6 orders records by `at`; chains are
evidence of each writer's own order.

## 8. Store

`.warrant/records.jsonl`: one canonical line per record, `\n`-terminated. `.warrant/blobs/<sha256>`:
blobs, each named by the hash of its bytes; only content that does not fit a body (> 16 384 bytes)
or is not JSON. `.gitattributes` sets `.warrant/records.jsonl merge=union`.

- **Canonical order:** distinct lines sorted by record id. Every write rewrites the file in it and
  `warrant fmt` restores it; `warrant assess` reports `canonical: false` for any other order and CI
  refuses that.
  A store with a rejected line is never canonical, wherever the line sorts, and `warrant fmt` reports it so.
  A writer refuses a record whose line its reader would reject.
- **Union merge:** two branches that append records merge without conflict. The reader accepts
  any order and identical duplicate lines (counted once). Two different lines with the same id
  differ only in `sig` (the id covers the rest): the record is authentic if any of its lines
  gives it a basis (a signature that verifies, or an unsigned line a migration vouches for, §9),
  and it is listed under `duplicates`. A line whose signature does not verify never revokes
  another line's basis. A line that is not canonical, is not a record, or exceeds
  65 536 bytes is rejected and listed; it never aborts the read. A blob whose bytes do not hash
  to its name refuses the whole read.
- **Snapshot digest:** SHA-256 over the sorted distinct lines and the sorted blob names with
  their digests. Moving the bytes elsewhere does not change it.
- **Limits:** records, bytes, refs per record and lineage depth are bounded (`warrant/store.py`
  `LIMITS`); a store beyond a limit is refused before it is assessed. Lineages that require lineages
  are bounded by the length of the longest such chain, computed from the records before any guard is
  evaluated: requires nested beyond `LIMITS["requires"]` refuse the store, whatever order its record
  ids put them in. The core is a pure function over bounded input, and the agent interface runs it in
  process (§13).

## 9. Migration from Warrant 2, and authenticity

`tools/migrate_v2_to_v3.py` (at the tag `history/warrant-2-2026-10-27`: it imports Warrant 2)
converts a v2 store deterministically: the same v2 store gives the same v3 record ids, byte for
byte, whoever runs it. This repository's store is its output for `b37328b2` (docs/HISTORY.md).

- A v2 signature covers a v2 id; it cannot carry over to a v3 envelope, and the migrator MUST
  NOT sign as the v2 actors. Each migrated record keeps its v2 `actor` and `at` and is stored with
  `sig: null`.
- Every v3 record is derived from v2 records of **one** actor (refused otherwise), each
  authentic under the v2 trust. The migrator writes the map `[[v3 id, [v2 record ids],
  [v2 blob hashes inlined]] …]` as a blob, and one `attest` of the reserved schema `migration@1`,
  signed by the migrator checker (`checker sha256:<D>`, D the digest of the migrator's whole
  import closure: the script, `warrant3/`, `warrant/`), whose `body.target` is the map blob and whose
  body names the v2 snapshot digest, the v2 trust digest and the counts. This record is the
  genesis of the v3 store.
- A `sig: null` record is **authentic** for a receiver iff an authentic `migration@1` attest by
  an actor holding the role `migrator` in its profile lists its id in its map. Its basis is
  reported as `MIGRATED`, never as `SIGNED`.
- The receiver who also holds the v2 store has a second, independent basis: **replay**.
  `tools/migrate_v2_to_v3.py verify` re-runs the migration from the v2 store the genesis names
  (its root and trust digests) and refuses any difference in ids. Its `IDENTICAL` means only
  that the re-derived migrated ids equal the store's unsigned ids: it does not check the
  destination's trust, profile, schemas, map or copied blobs. Signature (custody of the migrator's seed) and replay
  (re-execution) are distinct bases and are reported apart; neither is upgraded into the other.
- The map blob also lists `dropped` (each v2 member the migration does not carry, and why that
  is safe; a record whose dropped member has content is refused) and `declared` with `applied`:
  where a v3 record says more than its v2 records did. There is one declared rule: closures of
  one obligation that name no earlier closure are chained in filing order (v2 kept them as
  independent candidates; v3 would read them as a FORK). It applies to two live obligations.
- Migrated records are in no actor chain. The v2 chain order they had stays witnessed by the v2
  store the genesis names.

## 10. Assessment, trust and profile

`assess(snapshot, trust, profile, as_of)` is a pure function. Records dated after `as_of` are
not in the view. The **trust** binds keys to actors (`{"warrant": "trust/3", "keys":
{actor: [public hex…]}}`); it authenticates and authorizes nothing. The **profile** is the
receiver's own: `{"warrant": "profile/3", "roles": {role: [actor…]}, "quorum": {role: k}}`
(`quorum` optional). Roles decide whose schemas count, who may succeed, whose attestations meet a guard, whose challenges count, who
replays and who migrates. The same bytes give different verdicts to receivers with different
profiles; nothing in the store can grant a role.

The report, in one pass, holds: the snapshot digest, the assessment id (the digest of the
snapshot digest, the trust, the profile, `as_of` and the code identity), `completeness:
UNATTESTED`, rejected records with reasons, chain forks, schemas, every lineage (versions in
order, leaf, effective version, state, verdict `OK`/`FORK`, excluded successors), every
version's guard verdict (`NONE`/`MET`/`PENDING`/`INVALID`, with who accepted and what is
waited for), every challenge (counted, why, reproductions, standing), and the graph (nodes and
typed edges). **Reliance** on a lineage is `ELIGIBLE` iff it is not forked, its effective version
exists and no counted challenge stands against it; `CHALLENGED`, `PENDING` (nothing effective
yet), `FORK` otherwise.

## 12. Open limits

- R-FORK-RECOVERY: a forked lineage has no merge: a version names one predecessor, so a fork is
  permanent until a merge rule is specified (v2 claims let one supersession name both branches);
  union merge of the file does not resolve a semantic fork.
- R-EVIDENCE-PRESENCE (Codex): an accepted closure may name evidence that is not in the view;
  v2 §4.2 required it to resolve. Choose a per-schema or per-consumer availability rule before
  tools advertise a closure as portable.
- R-IMPOSSIBLE (Codex): `obligation@1` has no `impossible` state; how acknowledged
  impossibility differs from delivery and forgiveness, dependencies included, is undecided.
- R-REPLAY-SCOPE (Codex): `_vouch` trusts the migrator the profile admits; the checker-shaped
  name does not prove its key ran code D, and `verify` checks the migrated ids only (§9). The
  migrator's identity names Python 3.15 and cryptography 50.0.2: its replay needs them.
- R-LIVE-SCOPE-DROPS (Codex): §11's drops fit this repository's workload; they are not a proof
  that v3 keeps every v2 capability. A role-admitted checker's attestation is a trust decision,
  not the receiver's own compute replay.
- R-GATE-CLOSURE: the gate decides from `warrant/gate.py` (an owner path, run through the owner
  path `tools/gate.py`) and the rest of the `warrant` package (not an owner path), as Warrant 2's
  gate imported its engine: a change to the engine merged by the gate changes later merge decisions.
- R-UNION-ON-FORGE: GitHub's merge does not run the `union` driver; two pull requests that add
  lines next to each other in `records.jsonl` conflict there, and the second rebases (a local
  `git merge` applies `union`; `warrant fmt` restores the order).
- R-AGENT-CLOCK: the agent interface bounds an assessment by its input (§8, §13), not by a
  wall clock.
- R-PILOT-V2: `warrant_pilot/` keeps Warrant 2's Sigma receipt protocol (`compute.py`) and limits,
  and docs/PILOT.md shows Warrant 2 duty ids (read through the migration's map) to keep the bytes its
  accepted closures cite.
- No remembered-verdict cache (F44): the store is read and assessed in under half a second;
  signed records are verified on every read.

## 13. The agent interface (warrant-agent/3)

`warrant_agent` serves eight operations (workspace, context, read, graph, handoff, prepare, commit,
explain) through one backend: the Python API, the `warrant-agent` command and the stdio MCP server
`warrant-agent-mcp`. Its configuration is the operator's (docs/AGENT.md).

- Every operation that reads records reads the store once and assesses it in process: the store is admitted by size first (the workspace's `store_bytes`), then by the engine's limits.
- `commit` signs only a record whose actor is the configured signer (`NOT_PERMITTED`).
- The append is a compare-and-swap on the signer's head: a record whose `prev` is no longer the signer's head is refused (`CHAIN_MOVED`).
- A record whose body does not fit its schema, or whose lineage rule would exclude it, is refused at `prepare` and at `commit` (`INVALID_RECORD`), never filed.
- A schema record is refused unless its body is a schema body, its signer holds `schema/author`, and it is the root of a name no counted schema has or the successor of that name's counted leaf, by the root's actor, under the same name.
- A valid schema short of its quorum is filed: it is how a schema is proposed.
- A record of `migration@1`, a successor dated before what it succeeds, and a record whose signed line exceeds 65 536 bytes are refused (`INVALID_RECORD`); `prepare` dates a successor no earlier than what it succeeds.
- `prepare` and `commit` assess the store with the record: one after which the engine would refuse the store, reject a line or record, or list a problem it did not have, is refused (`INVALID_RECORD`).
- `commit` decides under the writers' lock, on the store as it is then, every raw line counted (rejected ones too), so no other writer's append can make a committed record leave the store refused; `prepare`'s answer is advisory and can go stale.
- `commit` refuses a seed whose key the workspace's trust does not bind to the signer (`SIGNER_NOT_TRUSTED`).
- An operation the operator did not permit for the workspace is refused (`NOT_PERMITTED`).
- A configuration that Warrant 2's `warrant-agent-mcp init` wrote (`agent_api` `warrant-agent/1`, its store a repository's `.warrant/store`) is read as that repository, with the same signer.
- `handoff export` carries every version of a target's lineage, what each rests on, and the attests and challenges on them and on those in turn, until nothing new is added.
- `warrant-agent-mcp init` creates no key: it refuses a seed whose key `.warrant/v3.json` does not bind to the actor (`INIT_KEY_NOT_PINNED`) and a seed inside the repository (`INIT_INSIDE_REPOSITORY`).
- `init` writes no path through a symlink (`INIT_SYMLINK`), and replaces an existing configuration only with `--force` and only when an init wrote it (`INIT_NOT_INIT_OUTPUT`).

## 14. This repository's loops

What follows binds the review loop's commands (`warrant.review`, `warrant.gate`, `warrant.claims`,
`warrant.roadmap`) as this repository runs them (docs/REPOSITORY.md); another receiver needs none of
it, and another repository that runs them configures them in its own `.warrant/`.

- The review loop's commands run on the repository `--root` names, else the Git checkout around the current directory, never on the package's own tree.

**The merge gate** (`warrant/gate.py`, an owner path) merges a pull request with no owner act when
the review loop accepted it:

- The head's store is read from the head commit as Git objects and assessed under the base's `.warrant/v3.json`, never the head's: a line it rejects, or a problem, refuses both verdicts (`STORE_PROBLEMS`).
- A head that proposes a valid schema short of its quorum is due for review: a pending schema is no problem of the store.
- After the head version's commit X, only lines added to `.warrant/records.jsonl` and blobs added under `.warrant/blobs/` may change (`TAIL_CHANGES`); a line removed refuses too.
- Every blob added after X is cited by a record added after X (`TAIL_BLOB_UNCITED`).
- Every record added after X is a verdict of a `pr/acceptor`, a version of this pull request's lineage or a record about one of them, or a replayer's result on a finding (`TAIL_RECORD_UNREVIEWED`).
- A change to one of the base's `owner_paths` refuses the merge, never the review (`OWNER_PATHS`).
- The head version's guard must be met by a `pr/acceptor` (`NO_ACCEPT`), and no counted finding may stand against it (`OPEN_FINDING`).
- Heads that fork refuse both verdicts (`HEAD_FORK`).
- X must have the tree the head version names (`HEAD_COMMIT`) and be an ancestor of the pull request's head (`HEAD_NOT_ANCESTOR`).
- A pull request of verdicts only must come from a branch of this repository (`VERDICTS_FORK`) under `codex/verdicts/` (`VERDICTS_BRANCH`), each verdict new (`VERDICT_NOT_NEW`) and on a version the base holds due for its actor (`VERDICT_NOT_DUE`).
- A version is due for an actor's verdict only when its guard waits for nothing but attests by a role the actor holds: no lineage it requires is open.
- A required check counts only from the workflow file `.warrant/merge.json` binds it to (`CHECK_AMBIGUOUS`).
- The gate reads the pull request and the base branch again just before it merges, and merges nothing when either moved.
- The owner's `hold` label refuses the merge (`PR_HOLD`).

**The claims** (`warrant/claims.py`):

- `check` reads the specification, the witness files and the mutant harness from the repository's `.warrant/claims.json`, and refuses a repository without one or one that names a path, or a link, leading outside it (`CONFIG`).

- `check` refuses a live claim whose sentence is not in docs/V3.md (`CLAIM_TEXT_MISSING`), a witness no test prints (`WITNESS_MISSING`), a mutant that is not in tests/mutants.py (`UNKNOWN_MUTANT`) or whose cases are not among the claim's witnesses (`MUTANT_OFF_CLAIM`), and a live Warrant 2 claim (`V2_CLAIM_LIVE`).
- The claims checker is the actor `claims-checker` and signs only with a key the trust binds to it.
- `check` does not refuse a valid schema short of its quorum.
- Each acceptance by the claims checker names the commit it ran at, that commit's tree, the checker's `code` there and its `env`.
- CI re-executes every acceptance by the claims checker new since the base at the commit it names, and refuses one whose `code` is not the checker's code at that commit (`CODE_DIFFERS`), whose claims check fails there or whose version is not the leaf of a live `backed` claim there (`CLAIM_PREFLIGHT`), or that does not hold again there (`CLAIM_REPLAY_DIFFERS`).
- An acceptance holds for its commit, and the claim guard does not match `code`: the view says whether a claim's acceptance is at the current tree outside `.warrant/`, and the checker accepts again a claim whose acceptances are all at other trees.

**The review replay** (`warrant/review.py`, the review waker):

- A finding's test is one new file under `tests/`, and its verdict is its own case's line: `FAIL` reproduces, `ok` does not.
- CI re-executes every replay new since the base at the commit it names, and refuses a different result (`REPLAY_DIFFERS`) and a replay that is not its finding's test at a head version from the one the finding targets on, at that version's commit (`REPLAY_NOT_DUE`).
- A checker's `code` is the digest of its whole import closure: a run that loaded a module of the repository outside it is refused.
- The replay checker is the actor `review-replayer`; each replay names the code that ran and its `env`, and CI refuses a replay whose `code` is not the replayer's code at the commit it names (`CODE_DIFFERS`).
- A checker's attest names the package's code at its commit where that commit's tree carries the package's source, and elsewhere the package installed where it is re-executed (`CODE_DIFFERS`).
- The waker serves each repository its configuration lists, each with its own base branch, mirror, state and worktrees, and wakes nobody for a base whose `.warrant/v3.json` names another repository.
- The waker reads the replayer's seed only as `<actor>.seed` in its seed directory, for the actor the base's `warrant.review identity` names and its `.warrant/v3.json` makes a replayer; an actor id that is not a plain name reads none.
- The waker commits a replay only as new lines of `records.jsonl` holding exactly the replay results the checker printed, each by the replayer.
- The waker publishes a verdict only when the base's own package finds it the acceptor's acceptance or challenge of exactly the version due, signed with a key the base binds to the acceptor, every blob it adds cited.
- A branch the waker resumes carries the verdict only if it adds exactly the verdict's lines, and its blobs as regular files.

## 15. Claims
